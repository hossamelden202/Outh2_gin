Security Overview

This OAuth2 authentication microservice implements industry-standard security practices to protect user data and prevent unauthorized access. The service uses JWT-based authentication with multi-layer validation, Redis-backed session management, and device-aware security controls.

Core Security Features

JWT Token Signing

HMAC-SHA256 algorithm for token signature verification

Token Versioning

Prevents token hijacking through version control

JTI (JWT ID)

Unique token identifiers prevent token reuse

Device Tracking

Session binding to specific devices and locations

Token Blocklist

Redis-backed revocation for logged out tokens

Expiration Validation

Automatic token expiration enforcement

OAuth2 Authentication Flow

The service implements the OAuth 2.0 Authorization Code Flow for secure third-party authentication.

Flow Sequence

  1. Authorization Request: Client redirects user to /oauth2/authorize/{provider} endpoint
  2. Provider Redirect: User is redirected to OAuth provider's authorization URL with client_id, redirect_uri, and scope
  3. User Consent: User grants permissions on provider's platform
  4. Authorization Code: Provider redirects back to callback URL with authorization code
  5. Token Exchange: Server exchanges code for access token using client_secret
  6. User Data: Server retrieves user information from provider using access token
  7. Database Operations: Create or update user record in PostgreSQL
  8. Session Creation: Generate JWT tokens and store refresh token in Redis
  9. Token Response: Return access and refresh tokens to client

JWT Security Implementation

Token Structure

JWT tokens contain three parts: Header.Payload.Signature

Payload Claims

Claim Purpose Type
username User's unique username String
email User's verified email address String
role User's access role (user/admin) String
id User's unique database ID Integer
exp Token expiration Unix timestamp Integer
iat Token issued-at Unix timestamp Integer
version Token version for hijacking prevention Integer
jti Unique JWT ID for token tracking String (UUID)
devid Device identifier for session binding Integer

Token Validation Process

1. Extract Bearer token from Authorization header 2. Verify HMAC-SHA256 signature using secret key 3. Validate token has not expired (exp claim) 4. Check token version matches user's database version 5. Verify token is not in Redis blocklist (revoked tokens) 6. Extract claims and set in context 7. Grant access if all validations pass
Signature Security: Tokens are signed with a strong secret key (256+ bits recommended) using HMAC-SHA256. This ensures tokens cannot be modified without detection.

Token Types

Token Type Lifetime Purpose Storage
Access Token 15 minutes API request authorization Memory (short-lived)
Refresh Token 30 days Obtain new access token HTTP-only secure cookie + Redis

Token Management and Refresh Strategy

Refresh Token Flow

  1. Client sends POST request to /oauth2/refresh with refresh token cookie
  2. Server validates refresh token signature and expiration
  3. Verify refresh token stored in Redis matches provided token
  4. Check token version matches user's current database version
  5. Generate new access token (15 min validity)
  6. Generate new refresh token (30 days validity)
  7. Store new refresh token in Redis with device identifier
  8. Return both tokens to client

Token Rotation Benefits

  • Reduced Attack Window: Short-lived access tokens minimize exposure if compromised
  • Server-Side Revocation: Refresh tokens stored in Redis allow immediate invalidation
  • Device Binding: Each token tied to specific device prevents cross-device usage
  • Version Control: Token version mismatch indicates hijacking attempt
Important: Refresh tokens are stored in HTTP-only, Secure, SameSite cookies to prevent XSS attacks. Never expose tokens in URLs or local storage.

Session Management and Device Security

Session Architecture

Sessions are managed using Redis with device-aware tracking:

Session Key Format: session:{userId}:{deviceId}:{jti}
This structure allows querying all sessions for a user or all sessions for a specific device

Geolocation (City, Country) Verify login location legitimacy IP-API service

Logout Mechanisms

Single Device Logout

User logs out from current device:

1. Validate refresh token from cookie 2. Remove refresh token from Redis for that device 3. Add access token to blocklist for 15 minutes 4. Clear refresh token cookie 5. Return success response

Global Logout (All Devices)

User logs out from all devices:

1. Get authenticated user from access token 2. Increment token_version in database 3. This invalidates all existing tokens (version mismatch) 4. Remove all refresh tokens from Redis for user 5. Add all access tokens to blocklist
Token Blocklist: Logged out tokens are cached in Redis with 15-minute TTL to prevent immediate reuse while reducing memory overhead

Security Best Practices

For Developers

  • Secret Key Management: Use strong, random secret keys (256+ bits). Never commit to version control. Rotate periodically.
  • HTTPS Only: Always use HTTPS in production. Tokens exposed over HTTP can be intercepted.
  • CORS Configuration: Restrict CORS headers to trusted origins only. Prevent token leakage to malicious sites.
  • Rate Limiting: Implement rate limits on authorization and token refresh endpoints to prevent brute force attacks.
  • Logging: Log all authentication events but never log sensitive data like tokens or passwords.
  • Database Security: Use parameterized queries to prevent SQL injection. Hash sensitive data appropriately.

For Users

  • Account Security: Use strong, unique passwords for OAuth provider accounts
  • Session Monitoring: Regularly review active sessions and log out from unfamiliar devices
  • Token Storage: Never share access tokens or refresh tokens. Treat them as passwords.
  • Browser Security: Keep browser and extensions up to date to prevent XSS attacks
  • Global Logout: Use "logout all devices" after password change to invalidate potentially compromised sessions
